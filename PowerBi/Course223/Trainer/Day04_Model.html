19:00–19:08 — افتح مشكلة العمل قبل الاوامر

شو احكي

مريم، خلينا نتخيل وصلك ملف فيه اهداف موظفين، وملف فيه علامات كل مؤشر، وملف فيه الاقسام. لو ربطناهم غلط، ممكن كل رقم يطلع شكله رسمي وهو غلط. اليوم رح نضمن ان التقرير يفهم كل موظف وكل هدف وكل KPI صح

شو اعرض

افتح KPIs.csv بجانب Objectives.csv و Employees.csv. خذ مثال KPI واحد يتبع Objective واحد وموظف واحد. اعرض مخطط Employee → Objective → KPI → Assessment

تطبيق مريم

تقول بصوتها: ما الذي يمثله صف واحد بكل ملف؟ ومين الجدول الرئيسي الذي يصور عملية التقييم؟

الجواب: Grain في EvaluationScores صف واحد لكل AssessmentID؛ الوزن في Objectives؛ ليس لكل KPI وزن مستقل
  1. اسأل: هل KPIID مكرر داخل جدول KPIs؟ لا؛ بينما داخل EvaluationScores يظهر عبر جولات ومصادر مختلفة
  2. حدد AssessmentSource: Self وManager وUpward، لا تخلطهم في متوسط واحد
  3. اربط الاستخدام الحقيقي بملف الأهداف الذي عرضته: هو Objective Register وليس Assessment Fact

19:08–19:20 — استيراد كل مصادر البداية

ما بديك تحفظي ارقام بعينها، بديك تفهمي بنية ملفات المشروع وتقدري تضيفي ملفات جديدة الها علاقة فيه

Home → Get Data → Text/CSV → Transform Data، حمل: Directorates, Departments, Employees, StrategicPriorities, Objectives, KPIs, Calendar وEvaluationScores_2026_H1

تطبيق مريم

تفتح الملفات الثمانية، تحافظ على اسماء الاستعلامات بالانجليزي، وتتأكد كل File يظهر كجدول منفصل

لا تستخدم Folder Combine هنا، هدف اليوم النموذج وليس اعادة درس يوم 3
  1. يمكن تحميل جدول بعد الآخر، ثم Transform data لضبط الأنواع دفعة واحدة
  2. لو وقت التحميل طال، ركز على Employees, Objectives, KPIs, EvaluationScores أولا ثم باقي Dimensions
  3. لا تسمِّ ملف Excel أو ترفعه؛ الطالب CSV فقط

19:20–19:32 — المفاتيح والانواع: قصة الخطأ الصامت

شو احكي

الرقم اللي شكله ID لازم يظل Text حتى لو البرنامج حاول يخليه رقم. المفتاح مثل بطاقة الهوية، ما بجوز نقص منه صفر او يتبدل نوعه

شو اعرض

Power Query: حقول ID = Text، PlanYear/ObjectiveWeightPct/KPIScore = Numbers، Date/StartDate/DueDate/AssessmentDate = Date

تطبيق مريم

تعدّل نوع 3 حقول ID و3 قيم رقمية وتواريخ محددة، ثم Close & Apply

اختبار: EMP0001 نص؛ ObjectiveWeightPct عدد صحيح؛ KPIScore عدد عشري؛ Date تاريخ؛ Calendar[Date] مفرد
  1. في Evaluations لا تحول AssessmentRound مثل 2026-Q1 الى Date
  2. قيمة KPIScore ليست نسبة انجاز الهدف، ولا تعوّض الغائب بصفر
  3. على كامل البيانات: Check Distinct EmployeeID, ObjectiveID, KPIID, AssessmentID

19:32–19:47 — ابنِ السلسلة الأولى من العلاقات

شو احكي

لو ربطنا Tables بدون ما نسال مين الواحد ومين المتكرر، ممكن Power BI يعطينا Many-to-Many ونظن ان الحل اختيارها والسلام

شو اعرض

Model view → DirectorateID: Directorates 1:* Departments؛ DepartmentID: Departments 1:* Employees؛ EmployeeID: Employees 1:* Objectives

تطبيق مريم

تحدد جهة الـ One وجهة الـ Many، وتختار Single cross-filter direction وتأكد أن الخطوط Active

الحد الأدنى 3 علاقات صحيحة: Directorate → Department → Employee → Objective
  1. Manage relationships → New عند الحاجة، لا تعتمد على Autodetect بشكل أعمى
  2. اضبط Cardinality = One to many وCross-filter direction = Single
  3. إن ظهر Many-to-Many، ارجع لـ Data View وابحث عن Null أو Duplicate في مفتاح الـ One

19:47–20:02 — اكمل الطريق حتى سجل التقييم

شو احكي

اللي يحدد الأداء في النهاية علامة KPI، بس وزن الهدف لازم يظل بمكانه الصحيح حتى ما نجمعه 3 مرات

شو اعرض

StrategicPriorities[StrategicPriorityID] 1:* Objectives؛ Objectives[ObjectiveID] 1:* KPIs؛ KPIs[KPIID] 1:* EvaluationScores_2026_H1

تطبيق مريم

تكمل 3 علاقات وتشرح المسار الذي يجعل فلتر الموظف يصل لتقييم KPI

أصبح لدينا 6 علاقات قبل Calendar؛ 2026 assessments مرتبطة بأهداف 2026 فقط
  1. لو مصدر AssessmentID يحوي Q1 وQ2 فهذا ليس Duplicate بل تقييمات مختلفة
  2. لا تنشئ Relationship بين EvaluatorID وEmployees[EmployeeID] الآن: هذا دور مختلف (Role-playing) سنعود إليه لاحقا
  3. اكتب بجانب الشاشة: Weight lives at Objective grain, never at KPI score grain

20:02–20:14 — التقويم وسلوك الفلاتر

شو احكي

لو حطينا تاريخ التقييم، بدنا فلاتر زمنية تمشي بشكل مفهوم. Calendar رح نستخدمه باليوم السابع كمان، فبنؤسسه من الآن

شو اعرض

Calendar[Date] 1:* EvaluationScores_2026_H1[AssessmentDate]، Single Active؛ Table tools → Mark as date table → Date column

تطبيق مريم

تضع Calendar Year وQuarterLabel كسلايسر؛ وتختبر تغير عدد سجلات التقييم

2025 في Calendar ليس مشكلة، fact المتاح الآن تواريخه 2026-03-31 و2026-06-30 فقط
  1. Calendar مصدر منفصل يحتوي 2025–2026 وكل يوم فريد
  2. Mark as date table متاح عند اختيار Calendar في Data/Model view؛ تاريخ Date يجب أن يكون Unique وغير فارغ ومتصل
  3. إذا كان Date Auto-generated disabled فلا مشكلة، Calendar جاهز

20:14–20:27 — المفاجأة: ليش مجموع الاوزان زاد؟

شو احكي

مريم، تخيلي مدير سألنا: ليش مجموع اوزان الموظف ظهر 300 بدل 100؟ مش معناته بياناته غلط، ممكن احنا جمعنا وزن الهدف 3 مرات لأنه عنده 3 KPIs. كيف نثبت ان المصدر نفسه سليم؟

شو اعرض

Transform Data → Right-click Objectives → Reference → rename Objective_Weight_Audit؛ Group By EmployeeID وPlanYear مع Sum(ObjectiveWeightPct). قارن نتيجة audit بمستوى الKPIs

تطبيق مريم

تكتشف Reference بنفسها، تنشئ Query للوزن بدون العبث في المصدر وتشرح لماذا وزن الهدف ليس مستوى KPI

في الملف الأصلي: 4 Objectives لكل Employee-Year ومجموع ObjectiveWeightPct = 100. عدد مجموعات Employee-Year = 400
  1. Home → Group By → Advanced → EmployeeID + PlanYear؛ Sum ObjectiveWeightPct
  2. سمّي العمود TotalObjectiveWeight واغلق Enable load للاستعلام Objective_Weight_Audit بعد التحقق اذا ما بدك يظهر في Model
  3. سؤال سريع: Duplicate يأخذ نسخة خطوات مستقلة، Reference ينطلق من نتيجة الاستعلام الاصلي ويعتمد عليه؛ جرّبي المثال على نسخة لو بقي وقت
  4. لا تشرح DAX اليوم: تضخيم الاوزان هو السبب المهني الذي سيبرر تعلم DAX باليوم 5

20:27–20:39 — تحقق بصري بالـ Matrix وSlicer

تطبيق مريم

مرجع trainer: 10,023 تقييم Q1+Q2؛ Self 4,800؛ Manager 4,743؛ Upward 480. التحقق باستخدام Count وليس SUM(KPIScore)
  1. اختيار Distinct count لـ AssessmentID أو Count لأن المفتاح فريد
  2. سلايسر 2026-Q1 وQ2 مبني على Calendar QuarterLabel وليس AssessmentRound
  3. اذا لا يتغير Dept filter، راجع خطوط العلاقات والاتجاه
